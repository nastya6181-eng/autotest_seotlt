# Сверка вёрстки с макетом Figma

Тест открывает страницу сайта в браузере на ширине макета и сравнивает её с фреймом из Figma: шрифты, цвета, переносы строк, выравнивание и отступы. Результат — список конкретных расхождений вида ««Кластеры» — отступ от блока сверху: макет 470, сайт 798 (+328)», а не «страница не совпала на 90 %».

## Как это работает

**Опорные точки — тексты.** Заголовки, пункты меню, подписи и кнопки одинаковы в макете и на сайте, поэтому их можно найти без пометок в вёрстке: разработчикам не нужно расставлять `data-*` атрибуты.

1. Из SVG-экспорта Figma заранее извлекается каждый текст: строка, левый край, базовая линия, гарнитура, размер, начертание, цвет с прозрачностью, межбуквенный и межстрочный интервал, число строк.
2. Браузер (Playwright, Chromium) открывает страницу на ширине фрейма, прокручивает её, чтобы подгрузились ленивые блоки, и снимает те же параметры с каждого видимого текста.
3. Тексты сопоставляются один к одному. Повторы вроде «9 февраля 2026» в каждой карточке раздаются по близости, слайды за краем экрана отбрасываются.
4. У каждой пары сравнивается стиль, а положение — **относительно соседа сверху**, а не по абсолютным координатам.

Последнее важно. Если блок съехал на 20 px, все тексты под ним тоже сместились. Абсолютное сравнение покрасило бы их все. Относительное отмечает только сам съехавший блок: его отступ до соседа изменился, а у текстов ниже отступы прежние. Сдвиг всей страницы целиком ловится отдельно, по отступу самого верхнего текста от верха страницы.

## Где лежат данные

```
projects/<ключ>/design/
  pages.yml              список страниц сайта — отсюда тест берёт, что проверять (в git)
  main-1600.json         подготовленный макет главной (в git, десятки КБ)
  catalog-1440.json      подготовленный макет каталога
  src/                   исходники из Figma (НЕ в git)
    main-1600.svg
    main-1600.png
    catalog-1440.svg
```

| Что | Где | В git? | Зачем |
|---|---|---|---|
| Адрес сайта | секрет `SITE_<КЛЮЧ>` | нет, секрет | откуда открывать страницы |
| Список страниц, пути, зоны, допуск | `pages.yml` | да | что и как проверять |
| Подготовленный макет | `<имя>-<ширина>.json` | да | эталон, с которым сравнивается сайт |
| SVG / PNG из Figma | `src/` | **нет** (`.gitignore`) | из SVG готовится JSON; PNG — для людей |

Почему SVG не в git: экспорт главной весит 58 МБ, почти всё — векторный узор фона. В JSON остаются только тексты, это около 80 КБ. Исходники храните на общем диске команды и кладите в `src/`, когда готовите или обновляете макет.

Ключ сайта — суффикс имени секрета в нижнем регистре: секрет `SITE_INNOTECH` даёт ключ `innotech` и папку `projects/innotech/design/`. В проверку попадают только сайты, у которых есть и секрет, и `pages.yml`.

### pages.yml

```yaml
- name: main                 # имя страницы: задание в CI, папка отчёта. Латиница, цифры, «-»
  page: /                    # путь на сайте, от корня
  width: 1600                # ширина фрейма = ширина окна браузера
  design: main-1600.json     # подготовленный макет
  source: src/main-1600.svg  # исходник, из которого готовится JSON (для prepare)
  dynamic:                   # зоны с меняющимся контентом (см. ниже)
    - [880, 1320]
  tolerance: 2               # допуск по положению, px (см. ниже)
```

Обязательны `page` и `design`. Если `name` не указан, он берётся из имени JSON (`main-1600`). `width` по умолчанию берётся из макета.

## Подготовка макета из Figma

1. Открыть файл в Figma и выделить **фрейм страницы целиком**, а не группу внутри него.
2. Справа внизу **Export** → добавить формат **SVG**:
   - масштаб **1x**;
   - в настройках экспорта (⋯) **снять «Outline text»**. Иначе текст превратится в кривые, и тексты не извлекутся. Тест в этом случае упадёт с подсказкой, молча «ошибок нет» не будет;
   - «Include "id" attribute» не обязателен.
3. По желанию добавить ещё **PNG** того же фрейма, 1x. Тест его не использует, он нужен людям, чтобы сверять глазами.
4. Нажать **Export frame**.

Имена файлов не важны, команда `add` переименует их сама.

## Новая страница

Пример: каталог `/catalog/`, фрейм шириной 1440.

1. Выгрузить SVG (и PNG) по инструкции выше.
2. Одна команда копирует исходники в `src/`, готовит JSON и дописывает страницу в конец `pages.yml`. Комментарии в файле сохраняются.
   ```bash
   python design/design_compare.py add --site innotech --name catalog --page /catalog/ \
       --svg ~/Downloads/Каталог.svg --png ~/Downloads/Каталог.png
   ```
   Ответ: `Страница catalog (/catalog/) добавлена: catalog-1440.json — текстов 214, ширина 1440.`
3. Отметить динамические зоны в `pages.yml` (раздел ниже).
4. Проверить локально и, если нужно, поправить зоны:
   ```bash
   SITE=innotech DESIGN_PAGE=catalog python design/design_compare.py run
   ```
5. Закоммитить `pages.yml` и новый JSON. Папка `src/` в git не попадёт.

Ограничения команды `add`: имя только из латиницы, цифр и `-`; путь начинается с `/` и без `#`; страницу с уже существующим именем `add` не перезапишет, для обновления есть `prepare`.

## Дизайнер обновил макет

1. Выгрузить фрейм заново и положить SVG в `src/` **под тем же именем**, что указано в `source`, например `src/main-1600.svg`.
2. Перегенерировать JSON. Можно для одного сайта или для всех сайтов с макетами сразу:
   ```bash
   python design/design_compare.py prepare --site innotech
   python design/design_compare.py prepare
   ```
   ```
   innotech:
     ✔ main: main-1600.json — текстов 302, ширина 1600
     – catalog: исходника нет (src/catalog-1440.svg), JSON не трогаю
   ```
3. Проверить, что динамические зоны ещё попадают на свои блоки: если макет сильно перестроили, координаты могли уехать.
4. Закоммитить JSON. По дифу в git видно, что именно поменялось в макете: тексты, размеры, цвета.

## Динамические зоны

Новости, слайдеры, календари, ленты событий меняются без правки макета. Тексты в макете там — пример, на сайте будут другие. Если их не исключить, отчёт заполнится ложными «не найдено» и «переставлено». Такие места отмечаются в `dynamic`, тексты оттуда не сравниваются:

```yaml
dynamic:
  - [880, 1320]                # полоса на всю ширину: y от 880 до 1320
  - [200, 6060, 560, 6620]     # прямоугольник: x1, y1, x2, y2
```

Координаты — в пикселях **макета** (не сайта). Взять их можно в Figma: выделить блок, справа видны X, Y, W и H. Тогда `[X, Y, X+W, Y+H]`, или `[Y, Y+H]` для полосы на всю ширину.

Заголовки секций и статичные кнопки («Смотреть все») лучше оставлять вне зон, они как раз должны совпадать. Сколько текстов ушло в динамику, видно в строке покрытия лога: `динамических пропущено 130`.

## Допуск по положению

Сдвиги левого края и отступов в пределах допуска — норма, тест они не красят. Сравнение идёт в целых пикселях, тех же, что видны в отчёте: «−10, допуск ±10» считается нормой. **Стиль** (размер шрифта, начертание, гарнитура, цвет) сравнивается точно, без допуска.

| Где | Как | Когда применять |
|---|---|---|
| по умолчанию | 2 px | ничего не задано |
| `pages.yml`, у страницы | `tolerance: 10` | постоянная норма для этого макета |
| поле `tolerance` при ручном запуске (локально `DESIGN_TOLERANCE_PX=10`) | `10` | разово, на один прогон; перекрывает `pages.yml` |

Пример на главной Иннотеха: при допуске 10 px из отчёта уходят сдвиги в 3–9 px (подписи рейтинга, «Малый конференц-зал»), а крупные (+102 у статистики, +328 у «Кластеров») остаются. Замечаний по отступам и левому краю становится примерно на треть меньше.

Допуск указан в отчёте в двух местах: в строке покрытия (`допуск ±10 px`) и у каждого замечания о положении (`… (−12), допуск ±10`).

## Запуск локально

Один раз:
```bash
python3 -m venv venv
./venv/bin/pip install -r requirements-design.txt
./venv/bin/python -m playwright install chromium
```

Адрес сайта — в `.env` в корне репозитория, как у общих проверок:
```
SITE_INNOTECH=https://inno.seotlt.ru/
```

Запуск:
```bash
SITE=innotech ./venv/bin/python design/design_compare.py run                      # все страницы сайта
SITE=innotech DESIGN_PAGE=main ./venv/bin/python design/design_compare.py run     # одна страница
SITE=innotech DESIGN_TOLERANCE_PX=10 ./venv/bin/python design/design_compare.py run   # с допуском 10 px
```

Отчёты:
- `reports/innotech-design/` — все страницы;
- `reports/innotech-design-main/` — одна страница.

Внутри `summary.md` (то же, что на странице прогона), `findings.csv` (для Excel), `report.md`, `junit.xml`. Код выхода: 0 — расхождений нет, 1 — есть, 2 — макет пустой или не читается.

Если Chromium уже скачан другой версией Playwright, можно не качать новый: `CHROME_PATH=/путь/к/chrome`.

## Запуск в GitHub Actions

Actions → **Design checks** → **Run workflow**. Расписания нет, только ручной запуск.

| Поле | Что | По умолчанию |
|---|---|---|
| `site` | ключ сайта или `all` | `all` |
| `page` | имя страницы из `pages.yml` | пусто — все страницы |
| `tolerance` | допуск по положению, px, на этот прогон | из `pages.yml` или 2 |

Как устроен прогон:

```
infra ──► design (innotech · main)    ─┐
      ├─► design (innotech · catalog) ─┼─► logs
      └─► design (lazun · main)       ─┘
```

1. **infra** — самопроверка кода и матрица «сайт × страница»: секреты `SITE_*`, умноженные на страницы из их `pages.yml`. В матрицу попадают ключ сайта, имя секрета и имя страницы, адресов в ней нет.
2. **design (сайт · страница)** — отдельное задание на каждую страницу. Ставит Playwright с Chromium, получает **только секрет своего сайта** и в шаге «Тест: макет» сравнивает одну страницу. Задания идут **параллельно**.
3. **logs** — общая таблица по всем страницам на странице прогона и результаты во вкладке Checks.

**Параллельность.** Сколько страниц проверяется одновременно, задаёт переменная репозитория `DESIGN_PARALLEL` (Settings → Secrets and variables → Actions → Variables), по умолчанию 4. На бесплатном тарифе GitHub до 20 одновременных заданий на аккаунт, 4–6 — разумно, чтобы не забирать очередь у общих проверок. Каждое задание открывает одну страницу, поэтому время прогона почти не растёт с числом страниц, пока их не больше `DESIGN_PARALLEL`.

Адреса и домены маскируются в логах так же, как в общих проверках. Полные кликабельные адреса включаются переменной `REPORT_FULL_URLS=true`, только для приватного репозитория.

## Как читать отчёт

В задании `design (сайт · страница)` → шаг «Тест: макет»:

```
Покрытие:
  / (1600, допуск ±2 px): текстов в макете 302, динамических пропущено 130, сопоставлено 122,
  в другом месте 2, не найдено 44
━━━ Тест «макет»: 11 правил ━━━
  ✘ design.missing         Текст из макета не найден на сайте — УПАЛО [warning] замечаний: 39
  ✔ design.font_size       Размер шрифта не как в макете — ок
  ✘ design.gap             Отступ до блока сверху не как в макете — УПАЛО [warning] замечаний: 36
  …
🟠 design.gap — Отступ до блока сверху не как в макете: 36
   Как исправить: Поправить вертикальный отступ между этим текстом и блоком над ним (margin/padding/gap).
   ✘ / (главная)
       что:      «КЛАСТЕРЫ»
       почему:   отступ от «Фонд содействия инновациям»: макет 470, сайт 798 (+328), допуск ±2
       контекст: …макет: y=5562, x=144…
```

- **Покрытие** — сколько текстов макета реально сравнилось. Если «сопоставлено» мало, а «не найдено» много, скорее всего, не размечены динамические зоны или в макете тексты-заглушки.
- **«макет X, сайт Y (±Δ)»** — значение в макете, на сайте и разница: плюс — на сайте больше или ниже, минус — меньше или выше.
- **«контекст: макет y=…, x=…»** — где искать в Figma: по этим координатам находится слой.
- Тот же отчёт с таблицами «страница / что / контекст» и «как исправить» лежит на странице прогона (Summary). Все замечания одной таблицей — в артефакте, файл `findings.csv`.

## Правила

| Правило | Что значит | Типичная причина |
|---|---|---|
| `design.missing` | текста из макета нет на сайте | блок не свёрстан, текст другой, текст картинкой, или забыта динамическая зона |
| `design.moved` | текст есть, но больше чем на 500 px от своего места | секции переставлены |
| `design.gap` | отступ до текста сверху не как в макете (самый верхний текст — от верха страницы) | margin, padding, gap |
| `design.left` | левый край не как в макете | отступ контейнера, сетка, выравнивание |
| `design.lines` | текст переносится на другое число строк | ширина блока, отступы, размер шрифта |
| `design.font_size` | размер шрифта | |
| `design.font_weight` | начертание: 400 / 500 / 600 / 700 | не подключён файл нужного начертания |
| `design.font_family` | гарнитура, точное совпадение | другая или запасная гарнитура в CSS |
| `design.color` | цвет текста с прозрачностью: `#FFFFFF 80%` | учитывается и `rgba`, и `opacity` элемента с предками |
| `design.letter_spacing` | межбуквенный интервал, px (допуск 0,3) | в Figma задаётся в %, в CSS — в em |
| `design.line_height` | межстрочный интервал многострочных текстов, px (допуск 1) | |

Все правила строгие (уровень warning): любое расхождение сверх допуска красит тест, как и в общих проверках.

## Ограничения

- **Сравнивается то, что совпало по тексту.** Блоки без текста (картинки, иконки, плашки) пока не проверяются. Тексты-заглушки в макете («Lorem ipsum») не сопоставятся и попадут в `missing`.
- **Пиксель в пиксель — с допуском и только на ширинах из макета.** Между ширинами (например, 1280 при макетах 1440 и 375) эталона нет.
- **Шрифт проверяется по CSS.** Если в CSS указан Montserrat, а файл шрифта не загрузился и браузер подставил запасной, тест этого не заметит.
- **Текст, спрятанный через `clip-path` или за другим элементом,** считается видимым.
- **Тексты под поворотом или масштабом в SVG** не сравниваются: их позицию из экспорта не восстановить. Их число печатает `extract`/`prepare`. Сдвиг групп (`translate`) учитывается.
- **Короткие символы** («²», «₽», «–»), если не нашлись, не считаются ошибкой. Цифры и буквы проверяются всегда.
